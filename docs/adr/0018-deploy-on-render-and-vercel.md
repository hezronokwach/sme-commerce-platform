# 0018: Deploy on Render and Vercel, with Vercel passing /api through

Status: Accepted (2026-11-24)

## Context

Issue "Deploy: Render + Vercel". The backend and Postgres go to Render, and the two frontends to Vercel.
The admin's refresh token is a `SameSite=Strict` cookie. A browser never sends such a cookie from
`*.vercel.app` to `*.onrender.com`, because they are different sites. Calling Render directly would
log every admin out when their 15-minute access token ends.

## Decision

1. **Each Vercel project rewrites `/api/*` to the Render backend** (`vercel.json`). The browser only ever
   talks to its own site:
   - the cookie stays first-party;
   - CORS isn't needed for the apps' own calls;
   - `apiBaseUrl` stays empty in both apps.

   Every other path is rewritten to `index.html`, so a refreshed deep link still loads the app.
2. **Render runs the Docker image** (`infra/render.yaml`), with a health check on `/actuator/health`.
   - The `prod` profile builds the JDBC address from Render's separate database values.
   - It trusts forwarded headers from private proxy addresses, so rate limits see the real client.
   - It turns Swagger off.
3. **Secrets are typed into Render's dashboard** (`sync: false`). `JWT_SECRET` is generated by Render.

## Consequences

- One more network hop for each API call, through Vercel.
- Live streams (SSE) also pass through Vercel's rewrite. If Vercel cuts long-lived responses, the stream
  reconnects. This is to be checked in "Buffer + live testing".
- If the name `sme-commerce-api` is taken on Render, the service gets another address, and both
  `vercel.json` files must be updated to match.
- The issue's Done-when, a sandbox M-Pesa payment, waits for the M-Pesa issues (#13, #14), which were
  moved later. Until then the live check uses the fake provider and Stripe test mode.
